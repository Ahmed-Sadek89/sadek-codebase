# Dashboard development instructions

All paths below are relative to the repository root. These rules apply to `apps/dashboard` alongside the repository's `AGENTS.md` instructions.

## Packages and imports

Keep this document current as part of every dependency change:

- When the dashboard starts importing a new workspace package from `packages/`, update this section with its package name, repository location, purpose, and supported import examples.
- When installing and using a new npm dependency in the dashboard, update this section with its package name, purpose, and how the dashboard uses it. Include development dependencies when they are used by dashboard tooling.
- When adding and using a dependency inside a shared package for dashboard functionality, document its purpose and the shared package that owns it.
- Update this `AGENTS.md` in the same change that introduces the dependency or its first use. Installing a package without using it does not require documenting it as used.
- When a documented dependency is removed or its usage changes, remove or revise its entry. Verify package names and import paths against the relevant `package.json` rather than guessing.

- `zod` defines the login validation schema and inferred form value types in `components/login/schema/login.ts`. Email must be present and valid; password must be nonempty. Password complexity rules belong to future authentication requirements.

- `packages/provider` supplies `QueryProvider` from `@repo/provider/query-provider` in the root layout; `packages/libs` supplies `getApiErrorMessage` from `@repo/libs/axios` in the login form hook. Libs owns Axios and TanStack Query configuration. The provider package owns `@tanstack/react-query-devtools`; `QueryProvider` also renders `@tanstack/react-query-devtools` only in development, initially closed; the dashboard does not configure a separate inspector.

Set it in `.env.local` before starting/building; `.env.example` uses `/api` for the proxy. An absolute URL sends browser requests directly to the backend, which must allow the dashboard origin through CORS. Keep `NEXT_PUBLIC_BACKEND_URL` in the dashboard's Turbo build/dev environment declarations.

Copy `.env.example` to `.env.local` if changing the origin, then restart/rebuild the dashboard. Keep `BACKEND_URL` in the dashboard's Turbo task environment declarations.

The auth layout header (`components/layouts/auth-pages-layouts/components/header.tsx`) uses it through `components/ui/theme-switcher` and `components/ui/language-switcher`, each with options in its own `utils/constants.ts`. It supplies the `animate-in`/`animate-out`, `fade-*`, `zoom-*`, and `slide-*` utilities that the shadcn dialog, dropdown menu, and select use for open/close transitions. `ConfirmAction` adds a fade, zoom, and slide-up on open, the reverse on close, and disables the animation when the user prefers reduced motion.
- `@repo/ui/sidebar` (`packages/ui/src/sidebar.tsx`, shadcn sidebar) and `@repo/ui/collapsible` build the dashboard sidebar. The sidebar is adapted from shadcn in three ways. Below `lg` (`packages/ui/src/hooks/use-mobile.ts`, breakpoint 1024) it renders in the vaul `Drawer` from the left instead of a `Sheet`, and `sheet.tsx` was removed. Its desktop classes use `lg:` instead of `md:`. Its `--color-sidebar-*` tokens are mapped onto the existing palette in `global.css`. `components/layouts/dashboard-layouts/index.tsx` wraps the header and content in `SidebarProvider` so the header toggles can use `useSidebar`; page content renders in `SidebarInset`. `components/layouts/dashboard-layouts/components/sidebar-section` renders `Sidebar collapsible="icon"` placed below the `h-16` header. The sticky `SidebarFooter` shows the current user and a logout button that opens `ConfirmAction`. `hooks/use-current-user.ts` provides the user's name, email, image, and initial to both the sidebar and the header user menu. The sidebar also brings `tooltip`, `separator`, and `skeleton` into `packages/ui`.

The root layout wraps the app in `ThemeProvider` with `enableSystem` and `defaultTheme` `"system"`; the provider defaults to `attribute="class"`, toggling the `.dark` class that switches the color tokens in `packages/ui/src/global.css`; `<html>` has `suppressHydrationWarning` and no hardcoded theme class. `ThemeSelect` calls `useTheme().setTheme` and renders the default until mounted to avoid a hydration mismatch.
- `next-intl` localizes the dashboard in English, Arabic, German, and Russian with locale-prefixed URLs (`/en/dashboard`, `/ar/dashboard`, ...). All pages live under `app/[locale]`, whose `layout.tsx` is the root layout: it validates the locale, sets `<html lang dir>`, and wraps the app in `NextIntlClientProvider` and `DirectionProvider`. Do not add `app/layout.tsx`: the locale must stay a root param. `next.config.js` wraps the config with `createNextIntlPlugin("./i18n/request.ts")`. `i18n/config.ts` holds `LOCALES`, `DEFAULT_LOCALE` (`"en"`), the `NEXT_LOCALE` cookie name, and `getDirection` (`rtl` for Arabic). `i18n/request.ts` reads the locale from the URL via `next/root-params`. `i18n/routing.ts` defines the routing (`localePrefix: "always"`, no locale detection), and `i18n/navigation.ts` exports locale-aware `Link`, `usePathname`, `useRouter`, `redirect`, and `getPathname`: use them instead of `next/link`/`next/navigation` for internal links, with locale-free hrefs (`"/dashboard"`). `usePathname` returns the path without the locale, which the sidebar's `isActivePath` relies on. The language select calls `router.replace(pathname, { locale })`. Messages live in `messages/{en,ar,de,ru}.json` as one flat object of camelCase string keys: no nested objects and no dots in keys (next-intl reads dots as nesting). `en.json` is the source catalog: `global.d.ts` types `useTranslations`/`getTranslations` keys against it, and `i18n/types.ts` exports `MessageKey` for constants that store keys (`labelKey`, `titleKey`). Add every new key to all four files. Server components use `getTranslations()` from `next-intl/server`, client components use `useTranslations()`, and page metadata uses `generateMetadata`. The login Zod schema is built by `createLoginSchema(t)` so validation messages follow the locale. Unknown paths under a locale hit `app/[locale]/[...rest]/page.tsx`, which calls `notFound()` to render the localized `app/[locale]/not-found.tsx`.
- `@repo/ui/direction` (`packages/ui/src/direction.tsx`, wrapping `radix-ui`'s `Direction`) exports `DirectionProvider` and `useDirection`. Radix primitives read the reading direction from it. `@repo/ui/sidebar` uses it to default `side` to the reading-start edge (right in RTL) and to place collapsed tooltips. Shared and dashboard components use logical Tailwind utilities (`ms-`/`me-`, `ps-`/`pe-`, `start-`/`end-`, `text-start`) and flip directional icons with `rtl:` variants, so prefer those over `ml-`/`pl-`/`left-`/`text-left`.
- Server prefetch + client query pattern (first used by `/{locale}/dashboard/skills/category`): the route's `page.tsx` holds both the SEO metadata (`generateMetadata`) and the prefetch. It calls `prefetchGuardedQueries` (or `prefetchPublicQueries`) from `libs/prefetch.ts` with the shared service from `@repo/services/*` and the key from `queryKeys` in `@repo/utils/query-keys`, then renders the root component inside `HydrationBoundary` (from `@repo/libs/query`) with the returned state. `page.tsx` has a single component, the default `Page`. It starts the prefetch as an async IIFE and renders the resulting promise as a child of `<Suspense fallback={<…Skeleton />}>`; React suspends on a promise child exactly as on an async component. Do not `await` the prefetch in `Page` itself, or the whole page waits and the fallback never shows. The page's root component from `components/<page>/index.tsx` holds all page content (heading, table, and so on) and takes no `children`; `page.tsx` renders it inside `HydrationBoundary`. The root component only renders UI. For tables, use the shared `<TableContentSkeleton />` from `components/ui/skeleton/table-content-skeleton` as the fallback; it takes no props. `getQueryClient`, `dehydrate`, and `HydrationBoundary` all come from `@repo/libs/query`. The client component calls the matching hook from `@repo/hooks/*` with the same query object, kept in the page's `utils/constants.ts`, so the hydrated cache is reused. Import `queryKeys` from `@repo/utils/query-keys`, not from `@repo/hooks`: the hooks entry is a client module. `prefetchQuery` never throws; when it fails or there is no token, the client hook fetches. Because no `staleTime` is set, the hook refetches in the background after hydration.
- Server prefetching goes through `libs/prefetch.ts` (server-only), never hand-written per page. `prefetchGuardedQueries(...queries)` reads `accessToken` from `auth()` and calls each `{ queryKey, queryFn: (auth) => service(..., auth) }`. `prefetchPublicQueries(...queries)` does the same for `{ queryKey, queryFn: () => service(...) }`. Both run the queries in parallel on a fresh per-request QueryClient (`getQueryClient`) and return the `DehydratedState` for `<HydrationBoundary state={state}>`. Neither ever throws: each failed query (e.g. a backend 500) is caught and logged as `[prefetch] <queryKey> failed: <getApiErrorMessage>`. Failed queries are not dehydrated, so the client hook refetches and the table's error UI (with `onRetry`) takes over. Signed out, the guarded helper fetches nothing.
- `@repo/utils` (`packages/utils`) supplies `queryKeys` from `@repo/utils/query-keys` for server prefetches. `@repo/hooks/category-skills` supplies `useCategorySkills` for the category-skills table. `@repo/services/user-company` (`userCompanyService.findMine`) and `@repo/hooks/user-company` (`useMyUserCompanies`) back the user-companies table. `@repo/services/what-can-do` (`whatCanDoService.findMine`) and `@repo/hooks/what-can-do` (`useMyWhatCanDos` and the create/update/delete hooks) back the what-can-i-do table. `@repo/hooks/users` (`useUpdateUser`) saves the profile form.
- `@repo/hooks/contacts` (`useContacts`, `useDeleteContact`), `@repo/services/contacts` (`contactsService.findAll` for the server prefetch), and `@repo/types/contacts` (`Contact`, `ContactsQuery`) back the contacts (Messages) table.
- `packages/constants`: `@repo/constants/twitter-card` (`TwitterCard`, `TWITTER_CARDS`, `DEFAULT_TWITTER_CARD`) supplies the share card sizes, labelled through `TWITTER_CARD_LABEL_KEYS` / `twitterCardLabelKey` in `components/seo/utils/constants.ts` (a `Record`, so a new size needs a label).
- `@repo/hooks/pages` (`usePages`, `useCreatePage`, `useUpdatePage`, `useDeletePage`) and `@repo/services/pages` (`pagesService.findAll` for the server prefetch) back the Pages table and the SEO page select and filter.
- `@repo/hooks/seo` (`useSeoList`, `useCreateSeo`, `useUpdateSeo`, `useToggleSeoActive`, `useDeleteSeo`), `@repo/services/seo` (`seoService.findAll` for the server prefetch), and `@repo/types/seo` back the SEO table.
- `i18n/request.ts` sets next-intl's `timeZone` to `"UTC"` so `useFormatter().dateTime` output matches between server render and hydration.
- `sharp` compresses uploaded images to WebP (quality 80; the 2 MB `UPLOAD_MAX_SIZE` is checked on the compressed image, returning 413 if still too large, while the form only size-checks documents) in `app/api/uploads/route.ts` (`POST /api/uploads`, multipart `file`, Node runtime only) before they are stored in S3; PDF/Word files are stored unchanged. The projects form calls it on submit through `uploadFile` and `deleteFile` (`libs/upload/upload-file.ts`, `libs/upload/delete-file.ts`; all upload code, including the server-only `s3.ts` and the shared `upload-types.ts`, lives in `libs/upload/`): it uploads a newly picked image, then creates or updates the row (`null` clears a removed image), then deletes the replaced or removed image through `DELETE /api/uploads/:id`, and deletes the new upload again if the save fails. Skills have no icon: a skill is just one `name` (the same in every language), its categories and `isActive`.

## Route pages

Every `apps/dashboard/app/**/page.tsx`, including `apps/dashboard/app/page.tsx`, contains:

1. SEO metadata for that specific page, using Next.js `Metadata` or `generateMetadata` for dynamic metadata.
2. An import of the page's root component from `apps/dashboard/components`.
3. A default page export that renders that root component, passing route data when needed.

Keep page UI, form logic, and hooks in the components directory. Keep `page.tsx` as a Server Component so it can export metadata; add `"use client"` only to components that need browser APIs or React client hooks. Root layout metadata supplies shared defaults, but each page should describe its own content.

Example for `apps/dashboard/app/page.tsx`:

```tsx
import type { Metadata } from "next";
import LoginPage from "../components/login";

export const metadata: Metadata = {
  title: "Sign in | Sadek Dashboard",
  description: "Sign in to your portfolio dashboard.",
};

export default function Page() {
  return <LoginPage />;
}
```

Use relative imports for local components unless an alias is explicitly configured in the dashboard's TypeScript configuration.

## Page component structure

Use the plural directory name `apps/dashboard/components`. Each page has its own folder with this structure:

```text
apps/dashboard/components/
  login/
    index.tsx
    components/
      login-form.tsx
    hooks/
    utils/
    schema/
      login.ts
  dashboard/
    index.tsx
    components/
    hooks/
    utils/
```

- `index.tsx` exports the root page component imported by the route's `page.tsx`. It composes the page using child components from its own `components/` folder.
- `components/` contains page-specific UI components. These components consume shared inputs, buttons, cards, and other primitives from `@repo/ui`.
- `hooks/` contains all custom hooks needed by that page.
- `utils/` contains static functions and static variables, such as arrays of objects, constants, and data transformation helpers. Functions here must not call React hooks.
- `schema/` contains HTML form field information and validation definitions for that page. Create this folder only when the page has a form; omit it entirely for pages without forms. Validate submitted data on the server when implementing authentication or data mutations.

Keep page-specific code within its page folder. Move reusable UI primitives into `packages/ui/src` instead of duplicating them across page folders. Add files to each supporting folder as needed.

## Dashboard shared UI structure

Store components reusable across dashboard pages in `apps/dashboard/ui`. Structure each component as `ui/<parent>/<child>/index.tsx`, grouping components by purpose:

```text
apps/dashboard/ui/
  forms/
    base-inputs/
      index.tsx
```

- `ui/` contains dashboard-wide reusable compositions. Keep page-specific components in `components/<page>/components`, and keep primitives shared across apps in `packages/ui/src`.
- Each child folder's `index.tsx` exports its reusable component. Import from that folder using a relative path; no dashboard path alias is configured.
- Compose shared shadcn primitives from `@repo/ui` and use only colors from `packages/ui/src/global.css`.
- Keep page schemas, field definitions, validation rules, and submission hooks in their page folders. Shared UI receives labels, input props, and validation messages through props.
- `@tanstack/react-table` (**v9**, not v8: `useTable` + `tableFeatures`, `createColumnHelper<typeof features, TData>()`, `table.FlexRender`, `row.getAllCells()`; no `useReactTable`/`getCoreRowModel`) powers `components/ui/dynamic-table`. Version-matched usage guides ship in the package's `skills/` folder.
- `components/ui/dynamic-table` exports the generic client component `DynamicTable<TData>({ title, description?, columns, data, getRowId?, isLoading?, isError?, onRetry?, showSearch? = true, showReload? = true, onReload?, isRefreshing?, pagination?, loadingMessage?, errorMessage?, emptyMessage? })`. `title` (required) renders as an `<h2>` above the table, and `description` (optional) as a short muted paragraph under it. The table is labelled by the title (`aria-labelledby`) and, when present, described by the description (`aria-describedby`). Pages that use it pass their main heading as `title` instead of rendering a separate heading. `columns` define each header name and how its body cells render. It renders one `<th>` per column and one row per item. State UI: `isLoading` with no rows keeps the real headers and shows 5 skeleton rows (`@repo/ui/skeleton`), `aria-busy`, and a screen-reader caption. `isError` with no rows shows a centered error panel (`role="alert"`, `CircleAlert` icon, `text-danger`). `isError` while rows are shown (a failed refetch) keeps the rows and adds a `danger` banner above the table. With no rows and no error, it shows the empty message. `onRetry` (pass the query's `refetch`) adds a "Try again" button (`tableRetry`) to both error UIs. Messages default to the `tableLoading`/`tableError`/`tableEmpty` translations. Write columns as plain objects typed `DynamicColumnDef<TData>[]` from `components/ui/dynamic-table/types/types.ts`: `{ accessorKey | accessorFn + id | id, header, cell: ({ row }) => ..., meta?, sticky? }`. `accessorKey` is narrowed to `DeepKeys<TData>`, so a misspelled key is a type error. `sticky: "start" | "end"` pins a column with logical `start-0`/`end-0` and an opaque background, so it flips in RTL; use it for actions. Per-column body-cell attributes go in `meta: { cellProps: { lang, dir, className, ... } }`. The same file holds `StickySide`, `DynamicTableColumnMeta`, `DynamicTablePagination`, and `DynamicTableProps`. `features.ts` holds `dynamicTableFeatures` (core features only, so no sorting, filtering, or pagination), and `index.tsx` re-exports all of it. Keep `columns` stable (`useMemo`). Table cells use the shared cell components from `components/ui/cells` (barrel `index.ts`; each in `cells/<name>/index.tsx`):
  - `TextCell({ value, weight?, tone?: "default" | "muted", size?: "sm" | "base", fallback? = "—" })` renders one truncated line with `dir="auto"`, so mixed Arabic/English text picks its own direction, and a `title` tooltip.
  - `StatusBadgeCell({ value, tone?: "success" | "neutral" | "warning" | "danger" })` renders a pill with a dot. It uses theme tokens only, and `success` maps to `primary` because the theme has no success token.
  - `TableActionsGroup({ actions, disabled? })` renders row buttons from `{ key, label, icon: LucideIcon, onClick, tone?: "danger", showLabel?, hidden?, disabled? }`. They are icon-only with `aria-label`/`title` unless `showLabel`, and stop click propagation. It renders nothing when every action is hidden.
  - `utils/format.ts` `localized(locale, en, ar)` picks the active locale's text from an English/Arabic pair and falls back to the other language.
- Define a page's columns in a `useColumns` hook at `components/<page>/hooks/use-columns.tsx` (default export), as `components/category-skills/hooks/use-columns.tsx` does. The hook calls `useTranslations`/`useFormatter`/`useLocale` and takes options `{ busy?, onEdit?, onDelete?, canUpdate?, canDelete? }` (all optional). Category skills appends its `actions` column (`id: "actions"`, `sticky: "end"`, visually hidden header) only when an action is both allowed and handled; currently the page passes none, and returns `useMemo<DynamicColumnDef<TData>[]>(() => [ ...column objects ], [deps])` so the array stays stable. The page component calls `const columns = useColumns()`.
- Route error and loading files (Next.js 16: `error.tsx` receives `{ error, retry }`; `retry()` re-fetches and re-renders the segment, and replaces the older `reset`). `app/[locale]/error.tsx` catches render errors on every locale page (auth and dashboard) with a full-screen 500 page. `app/[locale]/(dashboard)/error.tsx` and `app/[locale]/(dashboard)/loading.tsx` render inside the dashboard layout, so the header and sidebar stay usable. Both error files only render `components/ui/streams/server-error` (`ServerErrorPage({ error, retry, fullScreen = true })`): it shows Error 500, a translated title and description, the `error.digest` reference (matching the server log), a "Try again" button calling `retry`, and a "Back to home" link. It logs the error to the console. `loading.tsx` renders `components/ui/skeleton/page-content-skeleton` (`PageContentSkeleton`, which renders `TableContentSkeleton`). Errors in the root layout itself are not caught; that needs an `app/global-error.tsx` with its own `<html>`/`<body>`. Expected request failures are not errors: data requests still go through `libs/prefetch.ts`, which never throws, and the table's own error UI.
- `DynamicTable` renders as a card (`rounded-xl border bg-card shadow-sm`): a header, an optional error banner, the table (muted uppercase column headings, row hover, no border under the last row), and a footer separated by borders. The header is `components/ui/dynamic-table/components/table-header.tsx` (`DynamicTableHeader`). On the left it shows the title, a total-count badge (`pagination.total`; screen-reader text `tableTotal` uses ICU plurals per locale), and the description. On the right, stacking under them below `lg`, it shows `SearchInput` when `showSearch` (default `true`) and an outline refresh button when `showReload` (default `true`) **and** `onReload` are set. The refresh button is icon-only below `sm`, spins and is disabled while `isRefreshing`. Pass the query's `refetch` and `isFetching`. The table does not filter rows itself. List pages read `?search=`, `?page=`, and `?limit=`, in any combination, with `readListQueryParams` from `utils/list-query.ts`. The client passes `(name) => useSearchParams().get(name)`. The server `page.tsx` passes `recordParamReader(await searchParams)`. Both feed the page's query builder (e.g. `getCategorySkillsQuery`), so the prefetch key matches. `readListQueryParams` trims `search` and cuts it to 20 characters. It drops non-integer or non-positive `page`/`limit` and caps `limit` at `MAX_LIMIT` (30), so invalid URLs never reach the backend as a 400. Absent params are left out, and the page builder supplies defaults (category skills: `limit` 10).
- `DynamicTable` footer: pass `pagination` (the paginated response, `{ page, limit, total, totalPage }`; the category-skills page passes `data`). The footer shows `TableRowsSelect`, a range summary (`tableRange`, e.g. "41–50 of 95", `aria-live`), and, when `totalPage > 1`, `TablePagination`. It is hidden while the skeleton shows and when `total` is 0. Both footer parts live in `components/ui/dynamic-table/components/`:
  - `table-pagination.tsx` exports `TablePagination({ page, totalPage })`, built on shadcn `@repo/ui/pagination`. It shows first and last pages, the current page with one neighbour on each side, and ellipses beyond 7 pages. Links are real `href`s that keep the other params (page 1 removes `?page=`), so modifier-clicks open new tabs. Plain clicks call `updateUrlParams(..., "push")`, so Back works and there is no server render. Previous/Next are `aria-disabled` at the ends.
  - `table-rows-select.tsx` exports `TableRowsSelect({ limit })`, built on shadcn `@repo/ui/select` with `PAGE_SIZE_OPTIONS` (5/10/15/20) plus the current `limit` if the URL set another. Changing it writes `?limit=` and removes `?page=`. It renders `<SelectValue>{limit}</SelectValue>` so the server HTML is not blank before Radix hydrates.

## Dashboard NextAuth authentication

- `next-auth` v5 (currently beta) is owned by `@repo/libs` and dashboard. `@repo/libs/auth` exports `createAuth(backendUrl, authService, cookiePrefix)` for server-only use; dashboard `auth.ts` exports handlers, auth, signIn, and signOut. Libs delegates login, refresh, and logout to `@repo/services/auth`, passing the server backend URL per request. Libs owns the Axios client at `@repo/libs/axios`. The dashboard passes `authService` into `createAuth`; libs uses a typed service interface and does not import services, keeping the package graph acyclic.
- Dashboard login now uses `signIn("credentials")` from `next-auth/react`, replacing its use of the in-memory login hook. Other shared query hooks retain their existing independent behavior.
- NextAuth uses `/api/session`, leaving `/api/auth` for the backend proxy. SessionProvider polls every 30 seconds and refetches on focus; session checks refresh expired access tokens. JWT `exp` claims control access and refresh expiry. Refresh preserves the original refresh token because the backend returns only access_token. Expired refresh tokens and failed refresh discard the entire auth JWT and both backend tokens on the next session check. The refresh token is never included in browser session JSON.
- Logout calls the backend with a valid access token where possible and clears the local session even on backend failure. Dashboard has server and client session guards and a sign-out button.
- Configure `AUTH_SECRET` (strong random secret), `AUTH_URL` (dashboard URL with `/api/session`), and `BACKEND_URL`. Set `AUTH_TRUST_HOST=true` only with a trusted deployment proxy. These server variables are passed through dashboard Turbo tasks.

- The dashboard passes `"sadek-dashboard"` as the `cookiePrefix` argument to `createAuth`; shared NextAuth cookie names use that prefix, including `sadek-dashboard.session-token`. Cookie options inherit NextAuth defaults, including HttpOnly, SameSite, path, secure handling, and temporary-cookie lifetimes. Changing names requires signing in again.

- Route redirects are implemented only in `proxy.ts`, using the NextAuth `auth` wrapper. The matcher covers every path except `api`, `_next`, `_vercel`, and files with an extension. A URL without a locale prefix redirects to the same path under the `NEXT_LOCALE` cookie's locale, or `/en`; `Accept-Language` is ignored. The proxy refreshes that cookie to the URL's locale on every page request. Within a locale, dashboard routes without an access token redirect to `/{locale}`; authenticated requests to `/{locale}` redirect to `/{locale}/dashboard`. Unprefixed redirects such as logout (`/`) and the post-login `/dashboard` land in the user's current language through the cookie.

- Successful login passes `/dashboard` as NextAuth `redirectTo`, then uses a full navigation to `/dashboard` so the proxy evaluates the freshly issued session cookie. `libs/auth.ts` exports both `handlers` and `auth` from the same configuration.

- The client session exposes the access token and expiries, plus `session.user` `{ id, name, email, image }`; the refresh token stays in the encrypted session cookie. At sign-in, `authorize` returns `name` (the login response's `user.username`), `email`, and `image` (`user.avatar`); Auth.js stores them in the JWT as `name`/`email`/`picture` and builds `session.user` from them. The backend tokens carry only `sub`, so these fields come from the session, never from decoding a token. The `jwt` callback handles NextAuth's `trigger === "update"`: it copies a string `session.user.name`/`email` and a string-or-`null` `image` from `update({ user })` onto the token, and never touches the backend tokens.
- `hooks/use-current-user.ts` gives the header and sidebar the user's name (falling back to the email), email, image, and initial, read only from `useSession().data.user`. Access tokens refresh 30 seconds before expiry. Server-side auth reads `BACKEND_URL`, falling back to `NEXT_PUBLIC_BACKEND_URL`.
